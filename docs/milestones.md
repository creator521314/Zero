## 一、一条贯穿全文的原则

### 「测试通过」不等于「东西能用」

这是本计划排优先级的唯一依据，来自一次真实事故：`web_search` 曾 100% 失败
（唯一的后端要自建 SearXNG，而默认配置/向导/模板都不写 `[search]` 段），
当时 **257 个单测全绿**——因为没有人从 `default_tools()` 这条生产装配路径取工具、
也没有真的联网搜一次。

因此本计划对每个里程碑统一要求三条：

| 要求 | 说明 |
|---|---|
| **真实环境跑一遍** | 用真实 LLM + 真实配置，不是替身也不是构造出来的对象 |
| **对输出内容下断言** | 「不报错」不算通过，要看产出是不是对的 |
| **零配置路径必须可用** | 凡是「配了才生效」的能力，要么有免配置默认，要么给出指明改法的报错（这条就是上面事故的形态） |

配套已就位：`cargo xtask smoke`（`crates/agent-tools/tests/smoke.rs`）把工具的
装配路径、参数契约、真实输出都纳入了 `cargo xtask check` 门禁（commit `5010fd1`）。

## 六、下一步

按本文第一节的原则，推荐顺序：

1. ~~M1–M3~~ 已完成；
2. ~~M4.1–4.6~~ 已完成（2026-10-24）：三类真实任务跑通 = 一期 MVP 达成；

4. 三期手机端（新增 `Frontend` 实现，core 零改动）。

二期开工前建议先做一件事：**真实用一段时间**。M4 的三次任务都是一次性跑通，
真实的稳定性问题（长任务、断网重试、上下文膨胀）只有连续用才会暴露；而二期的
价值取决于被同步的内容值钱——先让它真的被用起来，再决定同步什么。

每完成一项，同步更新本文状态表与根目录 `PROGRESS.md`，并在「已验证」一栏写清
**怎么验证的**，而不只是「已完成」。

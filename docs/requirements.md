## 一、项目概述

### 1.1 一句话定义

> **一个由个人独占使用的、运行在自有设备上的、能实际动手干活的通用 AI Agent。**

### 1.2 愿景与终局形态

项目的长期目标（Vision）是构建一个**统一框架**，可安装于用户拥有的任意设备（个人电脑、手机、服务器、单片机），每个设备作为终端运行，以手机为权威数据源，设备间按数据重要性与紧急性分级同步，实现个人数据与助理能力的跨设备可用。

### 1.3 范围策略：分期实施（**本项目最重要的决定**）

经评估，上述终局形态是一个**分布式系统**，复杂度远高于普通应用。用户明确决定采取**收缩策略**：

| 阶段 | 范围 | 说明 |
|---|---|---|
| **一期（MVP）** | **单机通用 Agent**（PC 端 + 服务器端） | 砍掉全部分布式复杂度，先验证"Agent 能干活"这一核心价值 |
| 二期 | 跨设备同步、分级同步策略、AI 辅助合并 | 依赖一期沉淀的真实数据形态才能设计 |
| 三期 | 手机端 App、单片机接入、设备注册中心 | 手机端一期不交付 |

> **决策依据**：先证明「Agent 有用」，再证明「到处都能用」。这是正确的工程顺序，而非妥协。

## 二、目标用户与使用场景

### 2.1 用户画像

| 维度 | 描述 |
|---|---|
| 用户数量 | **单用户**（仅本人），无多租户需求 |
| 用户特征 | 具备开发能力，熟悉终端操作，对数据主权有强意识 |
| 使用环境 | 个人电脑、自有服务器（后续扩展手机、单片机） |
| 安全模型 | 因单用户，安全模型可大幅简化，无需多租户隔离 |

### 2.2 核心使用场景（用户亲述的三类真实任务）

| 场景 | 描述 | 能力要求 |
|---|---|---|
| **场景 A：开发程序** | 让 Agent 编写一段程序代码 | 代码生成、文件写入、可执行验证 |
| **场景 B：编写脚本** | 让 Agent 写一段自动化脚本 | 代码生成、环境感知、文件操作 |
| **场景 C：收集新闻** | 让 Agent 联网抓取新闻并汇总 | 网络访问、信息提取、结果产出为文件 |

### 2.3 场景特征归纳（**关键洞察**）

> 以上三类任务本质上是**同一类**：均属于「**让 Agent 在用户电脑上执行操作、访问网络、并产出文件**」的任务。

**得出重要结论**：本项目要的不是问答型聊天助手，而是**一个具备真实执行能力的编码型 Agent**（能操作电脑、能上网、能读写文件）。这一定位直接决定了后续的能力设计与安全设计。

## 三、功能需求

### 3.1 一期功能需求（MVP）

| 编号 | 需求项 | 优先级 | 说明 |
|---|---|---|---|
| FR-01 | 通用任务对话与执行 | P0 | 能接收自然语言任务并执行完成 |
| FR-02 | 文件读写能力 | P0 | 能创建、读取、修改文件（产出交付物） |
| FR-03 | 命令执行能力 | P0 | 能在本机执行 Shell 命令 |
| FR-04 | 网络访问能力 | P0 | 能联网检索、抓取信息（支撑新闻收集类任务） |
| FR-05 | 多模型接入 | P0 | 支持多家云端厂商 API，主要使用云端模型 |
| FR-06 | 本地模型接口预留 | P1 | 预留本地模型接口（插件位），一期不强制实现 |
| FR-07 | TUI 交互界面 | P0 | 终端用户界面（Terminal UI） |
| FR-08 | 任务级权限配置 | P0 | 见 3.2 权限模型 |
| FR-09 | 会话/任务记录 | P1 | 任务历史可查（为二期同步做数据准备） |

### 3.2 权限模型（用户已明确设计）

用户设计了**任务级三档权限**，把"自动化程度"与"安全性"的取舍权下放到**每个任务**，而非全局一刀切：

| 档位 | 名称 | 行为 | 适用场景 |
|---|---|---|---|
| L1 | **全自动** | 所有操作直接通过，不需确认 | 低风险、高信任任务 |
| L2 | **AI 审视** | 由 AI 判断操作是否安全，决定是否放行 | 日常任务（默认档） |
| L3 | **逐步确认** | 每个操作均需用户手动确认 | 高风险任务 |

> **评价**：这是一个成熟的设计。信任边界由任务决定，而非全局设定，兼顾了效率与可控性。

### 3.3 技术栈约束（用户指定）

| 项 | 决策 |
|---|---|
| 开发语言 | **Rust**（PC 端与服务器端统一） |
| 客户端形态 | **TUI**（终端界面），不做 GUI |
| 服务器端 | Rust 实现（一期作为普通终端定位） |
| 手机端 | App（**一期不交付**） |
| 沙箱 | **暂不考虑**（见第五章风险项） |

### 3.4 后续版本功能（需求已采集，暂不实现）

| 编号 | 需求项 | 说明 |
|---|---|---|
| FR-10 | 多端部署 | 统一框架安装于电脑/手机/服务器/单片机 |
| FR-11 | 数据分级同步 | 按下述四级频率调度 |
| FR-12 | AI 辅助数据合并 | 含强制备份与回滚 |
| FR-13 | 设备注册中心 | 各终端向服务器注册（二期引入） |
| FR-14 | 数据分层管理 | 持久化数据与任务临时信息分离 |
| FR-15 | 单片机接入 | 作为哑终端（纯信息输入输出端） |

## 四、架构需求（终局形态，一期不实现）

### 4.1 拓扑结构

```
                    ┌──────────────────────────┐
                    │   服务器（二期：数据中心  │
                    │   + 设备注册中心）        │
                    └────────────┬─────────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              │                  │                  │
     ┌────────┴────────┐  ┌──────┴───────┐  ┌───────┴────────┐
     │  手机（权威节点） │  │  电脑（完整   │  │ 单片机（哑终端）│
     │  完整 Agent      │  │  Agent）      │  │ 仅采集/执行    │
     └─────────────────┘  └──────────────┘  └────────────────┘
```

### 4.2 节点角色定义

| 设备 | 角色 | 说明 |
|---|---|---|
| **手机** | **权威节点（主）** | 个人数据的主存储，其他设备以其为准 |
| 电脑 | 完整节点 | 运行完整 Agent，有本地存储 |
| 服务器 | 一期：普通终端；二期：数据中心 + 注册中心 | 角色随时间演进 |
| **单片机** | **哑终端** | **不运行 Agent**，仅作信息输入输出端（数据采集上报 / 指令执行） |

> **关于服务器角色的澄清**：用户在前两轮给出过"仅当普通终端"与"可作为数据中心"两种表述，经确认为**时间上的先后关系**（一期普通端 → 二期数据中心），非矛盾。

### 4.3 数据同步分级机制（用户核心设计）

**判据：数据重要性 × 紧急性（二维分级）**

| 等级 | 判据 | 同步时机 |
|---|---|---|
| **紧急且重要** | 简洁、紧急 | **立即同步** |
| 常规 | 介于中间 | **每小时 / 每 2 小时** |
| 低优先 | 不重要且不紧急 | **每日夜间 12:00 批量同步** |

### 4.4 数据合并策略

| 项 | 决策 |
|---|---|
| 合并方式 | **AI 分析合并** |
| 安全保底 | **强制保留原始备份，支持回滚**（用户已确认采纳） |
| 等级判定权 | **A+ 方案**：用户手动标记为主 + AI 兜底猜测 |
| 无法合并时的兜底 | **待定**（见第六章） |

### 4.5 数据分层原则

| 数据类型 | 处置 |
|---|---|
| **持久化数据** | 跨设备同步、长期保留 |
| **任务临时信息** | **不一定合入持久库**；单机保留一段时间后自动清理 |

## 六、风险与待定事项

### 6.1 已识别的技术风险

| # | 风险 | 影响 | 应对建议 |
|---|---|---|---|
| R1 | **手机作为权威节点但不适合常驻服务** | 手机 OS 会杀后台、限制长驻进程；手机离线时权威节点消失，同步链路中断 | 二期需引入中心化会合点/中转，纯 P2P 方案不成立 |
| R2 | **AI 合并可能误删数据** | AI 会"自认为理解意图"而删掉认为冗余的内容，数据不可逆 | 已确认方案：强制备份 + 回滚 |
| R3 | **AI 合并对加密/二进制数据失效** | 图片、二进制文件 AI 无法理解与融合 | 需设计"无法合并则保留双份"的兜底策略 |
| R4 | **无沙箱的执行权限** | Agent 可全盘操作，存在误删/误改风险 | 用户已明确暂不考虑，记为**已知且已接受的风险** |
| R5 | **单片机算力不足以承载完整框架** | 单片机无法运行 LLM 及大部分同步协议栈 | 已降级为哑终端，风险已缓解 |
| R6 | **TUI 开发工作量被低估** | 滚动、流式输出、Markdown 渲染均需手写，会拖慢首版 | 用户已确认直接做 TUI，接受更长周期 |
| R7 | **一级同步的设备发现问题** | 一期若无中心，设备如何互相发现未定义 | 二期需明确（手动配置 or 局域网自动发现） |

### 6.2 待定项（需用户决策后才能进入设计阶段）

| # | 待定项 | 说明 | 影响 |
|---|---|---|---|
| **P1** | **模型来源倾向** | 用户已明确"以云端为主 + 预留本地接口"，但**未指定优先接入哪些厂商** | 影响 API 抽象层设计 |
| **P2** | **成本预算** | **完全空白**。每月可接受的 API / 服务器支出未定 | 直接影响模型选型与用量策略（无此约束无法做技术选型） |
| **P3** | **隐私底线** | 数据能否离开本机、可否发送至云模型，未明确表态 | 与"云端为主"存在潜在张力，需澄清 |
| **P4** | 临时信息保留时长 | "保留一段时间"具体是多久（7天/30天/任务完成即清） | 影响清理机制与存储设计 |
| **P5** | 无法自动合并时的兜底策略 | 覆盖旧的 / 保留双份待裁决 | 影响二期数据一致性设计 |
| **P6** | 二期设备发现方式 | 手动配置地址 / 同 WiFi 自动发现 | 影响二期网络层设计 |
| **P7** | 首发目标任务清单外延 | 除代码/脚本/新闻三类，是否还有其它高频任务 | 影响工具链与能力优先级 |

> **P2（成本预算）与 P3（隐私底线）是当前最紧迫的空白**——两者共同决定技术方案的可行边界。

## 七、附录：需求采集过程纪要

本项目需求通过 7 轮结构化追问逐步收敛，关键演化路径如下：

| 轮次 | 用户输入要点 | 需求演进 |
|---|---|---|
| 1 | 项目目的：创建供个人使用的 Agent | 愿景确立 |
| 2 | 运行于电脑/手机/服务器/边缘设备，数据共享 | 定位为跨设备数据共享助理 |
| 3 | 统一框架、任意设备可装、手机为主、各端本地存储、定期同步、规则决定存储位置 | 架构形态确立 |
| 4 | 每日 12:00 同步；单片机为哑终端；冲突自行合并 | 同步机制初步确立 |
| 5 | 同步分级（立即/小时/每日）；AI 分析合并；持久化与临时信息分离；服务器暂当普通终端 | 同步策略精细化 |
| 6 | 支持回滚；A+ 判定；临时信息超期清理；服务器可作数据中心（二期） | 补全安全与演进路径 |
| 7 | 最基本功能是一个能干活 Agent，其余后续扩展 | **范围收缩，确定 MVP** |
| 8 | Rust + TUI；任务为开发/脚本/新闻；三档权限；无沙箱；预留本地接口+云端为主 | 技术栈与安全模型落定 |
